
# Agents Module

## 1. Purpose

The `agents` folder contains the common Base Agent functionality and the Response Agent for the AI Agent Coordination and Decision Engine.

The Base Agent provides reusable functions that can help different specialized agents follow common standards.

The Response Agent uses the results from previous agents to prepare a final response for the user.

## 2. Files in This Folder

### base_agent.py

This file contains the reusable BaseAgent class.

It provides common functionality that specialized agents can use without duplicating the same code.

Its main responsibilities are:

- Validate agent input using Pydantic schemas.
- Create a standard successful AgentResponse.
- Create a standard failed AgentResponse with structured error information.
- Invoke the configured LLM.
- Record execution failures using logging.

**Important:** BaseAgent does not control the execution of other agents. Each specialized agent is responsible for implementing its own `execute(input_data)` method and business logic.

### response_agent.py

This file contains the ResponseAgent class.

Its main responsibility is to generate the final response for the user using information received from previous agents.

It performs the following tasks:

1. Receives the original user request and workflow context.
2. Loads the required prompt instructions.
3. Combines the user request with the information available in the workflow context.
4. Sends the prompt to the configured LLM.
5. Extracts the generated response.
6. Returns the result using the common AgentResponse structure.

The generated response is stored in the `final_response` field inside `result`.

### prompts/

This folder contains the text instructions used by the agents.

#### system_prompt.txt

Contains general instructions for an AI agent, including how to understand tasks, process information and provide accurate results.

#### response_prompt.txt

Contains instructions specifically for the Response Agent. It guides the agent in preparing a clear final response using the available workflow results.

## 3. Agent Execution Interface

All agents must follow the common execution interface defined in the shared Agent Contract.

```python
execute(input_data)
```

The common input structure contains:

- `task_id`: Unique identifier for the task.
- `user_request`: Original user request.
- `context`: Additional information required by the agent.

The common agent response contains:

- `task_id`: Original task identifier.
- `agent_name`: Name of the executing agent.
- `status`: Agent execution status.
- `result`: Structured output from the agent.
- `next_agent`: Optional information about the next agent.
- `error`: Structured error information or null.

Allowed agent statuses:

- `completed`
- `partial`
- `failed`

The actual workflow routing is controlled by LangGraph, not by the individual agents.

## 4. Base Agent and Specialized Agents

BaseAgent provides reusable helper functionality.

Other specialized agents can use these helpers for:

- Input validation.
- Standard response creation.
- Standard error creation.
- LLM invocation.
- Logging.

Each specialized agent maintains its own execution method and business logic.

For example:

- M4 handles Planning and Research Agents.
- M5 handles Analysis and Decision Agents.
- M2 provides the common Base Agent helpers and Response Agent.

The Base Agent does not replace or rewrite the existing business logic of other members' agents.

## 5. LLM Integration

The Response Agent uses the configured LLM through the Base Agent's `invoke_llm()` method.

The LLM configuration is maintained separately in:

`backend/core/llm_config.py`

The application settings are maintained in:

`backend/core/settings.py`

The actual provider-specific connection will be completed after the team selects the common LLM provider and model.

Currently, the Response Agent can be tested using a mocked LLM without requiring an API key.

## 6. Input and Output Example

### Example input

```json
{
  "task_id": "TASK101",
  "user_request": "Analyze monthly business performance",
  "context": {
    "analysis_result": {
      "key_findings": [
        "Sales decreased by 20%"
      ]
    },
    "decision_result": {
      "recommended_decision": "Improve customer service"
    }
  }
}
```

This is an illustrative input. The final workflow context keys will follow the structure confirmed by M7.

### Example response

```json
{
  "task_id": "TASK101",
  "agent_name": "response_agent",
  "status": "completed",
  "result": {
    "final_response": "The business experienced a decline in sales. Improving customer service is the recommended action."
  },
  "next_agent": null,
  "error": null
}
```

The actual response content will be generated by the selected LLM.

## 7. Error Handling

The Base Agent provides a common error response helper.

When Response Agent encounters an execution error, it returns a structured failed response.

Examples of possible errors include:

- LLM is not configured.
- LLM connection failure.
- Empty LLM response.
- Invalid generated result.

Technical error details are recorded in application logs. The user-facing response contains a standard error message.

Input validation errors are raised through Pydantic validation.

Additional provider-specific packages will be added after the LLM provider is selected.

## 9. How to Run Tests

Make sure the project's virtual environment is activated.

To test Base Agent:

```powershell
python -m pytest .\backend\tests\test_base_agent.py -v
```

To test Response Agent:

```powershell
python -m pytest .\backend\tests\test_response_agent.py -v
```

To run all backend tests:

```powershell
python -m pytest .\backend\tests -v
```

The current unit tests use temporary Pydantic schemas and mocked LLM responses. They do not require a live LLM connection.
